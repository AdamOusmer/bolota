# bolota showcase

The public-facing showcase site for `bolota`. Astro, static output, no server.
Every demo on the page (determinism proof, expression picker, states grid,
sequences, API reference) runs the real library, live, in the browser.

## Consuming the library

This site does **not** depend on `@luzir/bolota` via `file:../..`. It installs the
same compiled tarball an npm consumer would get, so what you see running
here is what actually ships, not a shortcut through the workspace's `src`.

```
bun run lib:pack
```

That one script:

1. `cd`s to the repo root and runs `bun run build` (the library's own
   `scripts/build.ts`, compiling `src` to `dist`).
2. Packs the result with `bun pm pack --destination test/site/.lib`,
   producing `.lib/luzir-bolota-<version>.tgz` — the exact artifact `npm
   publish` would upload (scoped-package tarball naming: `@luzir/bolota`
   packs as `luzir-bolota-<version>.tgz`, `@` dropped, `/` becomes `-`).
3. Installs that tarball into this site with
   `bun add ./.lib/luzir-bolota-*.tgz`, which records it in `package.json`
   (`"@luzir/bolota": "./.lib/luzir-bolota-<version>.tgz"`) and `bun.lock`
   (pinned by its own integrity hash) like any other dependency.

`.lib/` is gitignored — it's a build artifact, regenerated by `lib:pack`,
never committed. Re-run `lib:pack` any time the library changes; `bun install`
alone will not pick up a new build, since bun only refetches a `file:`/tarball
dependency when its own install step runs `bun add` again (or the lockfile
entry changes).

## Commands

| Command | What it does |
| --- | --- |
| `bun run lib:pack` | Build the library and (re)install it here as a packed tarball |
| `bun run dev` | Local dev server |
| `bun run build` | Static production build |
| `bun run preview` | Serve the production build locally |
| `bun run typecheck` | `astro check` across `.astro` files and the `src/scripts` TypeScript |
